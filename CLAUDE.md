# Supplements Research Vault Schema

You maintain a supplements research wiki in this Obsidian vault, focused on evidence-based supplementation for longevity and healthspan.

## Your Role

You are the writer. The human is the editor-in-chief. You propose changes; the human directs, reviews, and corrects.

You co-maintain this schema. When you learn something about the domain, discover a better pattern, or receive a correction, update the "Wiki Conventions" section at the bottom of this file.

## Specifications (Strict)

These data contracts enable tooling. Do not deviate from them.

### Vault Layout

- `raw/` — Immutable source documents for ingestion. Drop PDFs, articles, papers, or notes here. Read from here, never write (except converted `.md` files derived from non-markdown sources). This is the primary ingestion point for the wiki.
- `research/` — Deep-research reports generated by the foundry-research pipeline. Each supplement gets its own subdirectory (`research/sulforaphane/`, `research/creatine/`). Read-only after generation. These are also valid sources for wiki ingestion.
- `wiki/` — Your compiled knowledge base. You own this directory entirely.
  - `wiki/index.md` — Content catalog. Update on every ingest.
  - `wiki/log.md` — Chronological operation log. Append on every operation.
  - `wiki/synthesis.md` — Evolving high-level synthesis. Revise on every ingest.
  - `wiki/handoff.md` — Session handoff. Read at session start, update at session end.
  - `wiki/interactions.md` — Cross-supplement and supplement-drug interaction matrix. Update during ingest.
  - `wiki/debates.md` — Active disagreements between sources and hypotheses.
  - `wiki/decisions.md` — Append-only log of structural decisions.
  - `wiki/entities/` — Entity pages (supplements, compounds, brands, delivery forms).
  - `wiki/concepts/` — Concept pages (pathways, outcomes, biomarkers). Use `concept_type` frontmatter to distinguish.
  - `wiki/sources/` — Source summary pages (one per ingested source).
  - `wiki/comparisons/` — Head-to-head supplement comparisons.
  - `wiki/hypotheses/` — Testable claims connecting supplements → pathways → outcomes.
  - `wiki/stacks/` — Supplementation stack configurations with rationale.
  - `wiki/queries/` — Significant query answers filed as permanent pages.
- `templates/` — Page templates. Use as starting points for new pages.
- `purpose.md` — Human-owned research direction. Read for context during ingest and query. Never modify this file.

### Source Types and Ingestion

The vault ingests from two source locations:

1. **`raw/`** — Arbitrary sources (papers, articles, web pages, personal notes). The wiki-ingest skill handles staging, hashing, and optional PDF conversion.
2. **`research/`** — Foundry-research reports. Already structured markdown. Ingest directly via wiki-ingest with `--research <supplement>`.

Both paths go through the same extraction → audit → wiki-update pipeline.

After cleanup, a research directory contains:
- `report.md` — The final research report (primary source for wiki ingest)
- `sources/` — Downloaded source PDFs and metadata
- `notes/` — Reader notes on individual sources

### Frontmatter (Required on Every Wiki Page)

```yaml
type: entity | concept | source-summary | comparison | hypothesis | stack
sources: []
created: "YYYY-MM-DD"
updated: "YYYY-MM-DD"
status: current | stale
tags: []
```

Additional by type:
- entity: `entity_type` (supplement | compound | brand | delivery-form | pathway | biomarker), `aliases` (list of strings — abbreviations and synonyms, e.g. `[SFN, sulforaphane isothiocyanate]`)
- concept: `concept_type` (pathway | outcome | biomarker)
- source-summary: `raw_path` (string, path to source in `raw/` or `research/<supplement>/report.md`), `raw_hash` (SHA256 of source file — enables staleness detection), `study_type` (RCT | meta-analysis | observational | in-vitro | review | editorial | preprint)
- comparison: `subjects` (list of wikilinks)
- hypothesis: `supplements` (list of wikilinks), `pathways` (list of wikilinks), `outcomes` (list of wikilinks), `evidence_level` (1-4), `hypothesis_status` (open | supported | contradicted | nuanced)
- stack: `goal` (string), `supplements` (list of wikilinks to supplement entities)

### TLDR (Required)

Every wiki page: `> [!tldr]` as the first content block after frontmatter. One sentence. The index extracts this.

### Claim Typing (Required)

- `> [!source]` — Fact from a source. MUST include `[[source]]` link.
- `> [!analysis]` — Your inference. MUST show reasoning.
- `> [!unverified]` — No authoritative source. Flagged for verification.
- `> [!gap]` — Explicitly missing. NEVER fill with a guess. Use `- [ ]` checkbox syntax inside gap callouts so gaps surface in `obsidian tasks`.

If you are paraphrasing, synthesizing, or inferring, use `[!analysis]`, not `[!source]`.

When multiple sources support the same claim, cite all of them:
`> [!source] Claim text. [[Source A]], [[Source B]]`

When new evidence confirms or contradicts a past `[!analysis]`, add a follow-up callout on the same page referencing the original claim. This builds a calibration trail — future sessions can see which analyses held up.

### Confidence Calibration

When new evidence addresses an existing `[!analysis]` callout, add a follow-up directly below it:

```
> [!analysis] Original inference. (reasoning)
> **[YYYY-MM-DD update]:** Confirmed by [[New Source]]. / Contradicted by [[New Source]].
```

This lets the wiki accumulate a track record of which inferences held up, improving trust calibration over time.

### Evidence Levels

When assessing the strength of evidence for a supplement-outcome pair, use these levels:

| Level | Label | Description |
|-------|-------|-------------|
| 1 | Mechanistic | In vitro or molecular evidence only |
| 2 | Preclinical | Animal model evidence |
| 3 | Biomarker RCT | Human RCT showing biomarker changes |
| 4 | Clinical endpoint RCT | Human RCT showing disease/mortality/functional outcomes |

Tag supplement entity pages with their highest demonstrated evidence level for each claimed outcome.

### Cross-References

All cross-references use wikilinks: `[[Page Name]]`. Not markdown links. The graph depends on this.

### Page Naming

Page filenames use Title Case with spaces: `Sulforaphane.md`, linked as `[[Sulforaphane]]`. The filename must match the wikilink text exactly.

No special characters beyond spaces and hyphens. Disambiguate with parentheticals: `NAC (Supplement).md`.

Supplement entities should have `aliases` set in frontmatter for common abbreviations and synonyms (e.g. SFN, NMN, TMG). This lets wikilinks like `[[SFN]]` resolve correctly in Obsidian without creating separate pages. Use `obsidian aliases` to audit coverage.

### Index Format

`wiki/index.md` is DataView-driven. Do not manually edit it — it auto-updates from page frontmatter. Your job is to ensure frontmatter is correct on every wiki page (type, entity_type, concept_type, hypothesis_status, evidence_level, sources list, tags).

`wiki/research-backlog.md` is also DataView-driven. Do not manually edit it. It auto-surfaces open-question pages, open hypotheses, thinly-sourced pages, and stale pages.

### Log Format

`wiki/log.md`: append-only. Each entry:
`### [YYYY-MM-DD] operation | description`
Log every ingest, query that generates a page, and lint pass.

### Other Conventions

- Tags in frontmatter, not inline. See Tag Taxonomy below.
- Dates in ISO 8601.
- One page per entity. Search before creating to avoid duplicates.
- When sources disagree, surface the disagreement explicitly.
- Prefer targeted updates over full page rewrites.
- Every ingest and query updates the wiki. Log and synthesis updates are part of the deliverable. The index and backlog are DataView-driven and update automatically — ensure frontmatter is correct instead.
- If a page grows past ~1,500 words, consider splitting it.
- Mark pages with open questions using the `open-question` tag so they surface in the Research Backlog.

### Tag Taxonomy

Tags serve as a secondary navigation layer for Obsidian's tag pane and graph view. Use alongside frontmatter, not instead of it.

- `supplement/<name>` — e.g., `supplement/taurine`, `supplement/sulforaphane`
- `pathway/<name>` — e.g., `pathway/nrf2`, `pathway/mtor`
- `outcome/<name>` — e.g., `outcome/cardiovascular`, `outcome/cognitive`
- `evidence/level-1` through `evidence/level-4` — evidence strength
- `open-question` — pages with unresolved `[!gap]` callouts
- `meta` — vault maintenance pages (index, backlog, log)

### Tooling Approaches

The Obsidian CLI is the preferred interface when Obsidian is running. Direct file I/O is the fallback.

| Operation | CLI (preferred) | Direct fallback |
|-----------|-----------------|-----------------|
| Create page | `obsidian create name="..." path=<dir> template=<template-name>` | Read template, write new page |
| Read page | `obsidian read path=<path>` | Direct file read |
| Append to page | `obsidian append path=<path> content="..."` | Read → Edit |
| Prepend to page | `obsidian prepend path=<path> content="..."` | Read → Edit |
| Rename/move page | `obsidian move path=<old> dest=<new>` | Edit file + grep-replace wikilinks |
| Full-text search | `obsidian search query="..." path=<dir>` | `grep -ri "..." wiki/` |
| Search with context | `obsidian search:context query="..." path=<dir>` | `grep -ri -C 3 "..." wiki/` |
| Backlinks | `obsidian backlinks file="<page>"` | `grep -rl "[[<page>]]" wiki/` |
| Outgoing links | `obsidian links path=<path>` | Parse wikilinks from file |
| Orphans | `obsidian orphans` | Parse files, diff against wikilinks |
| Dead ends | `obsidian deadends` | Parse files, find no-outgoing-link pages |
| Unresolved links | `obsidian unresolved` | Collect wikilinks, diff against filenames |
| Read property | `obsidian property:read name=<prop> file=<page>` | Parse YAML frontmatter |
| Set property | `obsidian property:set name=<prop> value=<val> file=<page>` | Edit frontmatter |
| List aliases | `obsidian aliases` | Parse `aliases:` frontmatter |
| List tags | `obsidian tags counts` | Parse frontmatter tags |
| Tag info | `obsidian tag name=<tag> verbose` | Grep for tag |
| Query base | `obsidian base:query file=<base> format=json` | Read .base file |
| Open tasks/gaps | `obsidian tasks filter="todo"` | `grep -r "- \[ \]" wiki/` |
| File outline | `obsidian outline file=<page>` | Read headings |

CLI gotchas:
- Use `path=<dir>` to scope search, not `folder=<dir>`.
- `obsidian create ... template=<name>` requires the Templates core plugin enabled.
- `obsidian move` auto-updates all wikilinks vault-wide. Always prefer it over manual file rename.
- `obsidian append/prepend` is preferred for log and index updates — avoid read→edit→write cycles when only adding content.
- CLI requires Obsidian desktop to be running. Fall back to direct I/O when it's not.

## Guidance (Flexible)

### Entry Points

Orient before acting. Minimum read set by task — do not read the full wiki first, navigate by wikilinks:

| Task | Read first | Then |
|------|-----------|------|
| Any task | `wiki/handoff.md` | — |
| Ingest | `purpose.md` → `wiki/synthesis.md` | Related entity/concept pages from index |
| Query | `wiki/synthesis.md` → `wiki/index.md` | Relevant entity/concept pages |
| Stack design | `purpose.md` → `wiki/synthesis.md` | Entity pages for candidate supplements |
| Interaction check | `wiki/interactions.md` | Relevant entity pages |
| "What's next?" | `wiki/research-backlog.md` → `purpose.md` | — |
| Lint | `wiki/research-backlog.md` | Full wiki scan |
| Contradiction check | `wiki/debates.md` | Linked hypothesis pages |

Always read `wiki/handoff.md` first — it captures what the last session was doing. Always update it at session end.

`wiki/synthesis.md` is the fastest entry point for most tasks. Read it before reading individual pages.

### Writing Style

See `writing-style.md` for examples and before/after pairs.

- Funnel structure. Lead with conclusions.
- Plain language, short sentences.
- No hedging stacks. One qualifier max.
- Define acronyms on first use per page.
- State assumptions explicitly.

For `comparisons/`, `stacks/`, and `synthesis.md`: translate findings into practical implications ("so what"). Qualify cross-source comparisons when sources differ in scope or method.

### Ingest

Your goal is to extract knowledge from a research report and integrate it into the wiki. Read `purpose.md` for context on the human's research direction.

For research reports in `research/<supplement>/report.md`:
1. Read the full report.
2. **Contradiction sweep:** Search existing `[!source]` claims related to the supplement's key topics before writing. Surface conflicts in the pre-check.
3. Before writing pages, present the human with: (1) key takeaways, (2) planned new pages, (3) existing pages to update, (4) potential contradictions found in step 2.
4. After approval, create and update wiki pages.
5. Update synthesis, interactions, debates, decisions (if applicable), handoff, and log.

For each supplement, create at minimum:
- An entity page for the supplement itself (with evidence-level tagging)
- Concept pages for key mechanisms and outcomes (e.g., Nrf2 Signaling, Cardiovascular Health)
- Hypothesis pages for significant claims that cross-cut or carry tension
- A source-summary page linking to the research report
- Stack-relevant notes (dosing, timing, form, interactions)

### Supplement Entity Pages

Each supplement entity page should address:

1. **What it is** — Chemical class, natural sources, available forms
2. **Mechanism of action** — Primary validated pathway(s)
3. **Evidence by outcome** — Organized by evidence level (mechanistic → clinical endpoint)
4. **Dosing** — Studied dose ranges, optimal form, timing considerations
5. **Safety profile** — Known side effects, drug interactions, contraindications
6. **Interactions** — With other supplements, medications, or conditions
7. **Practical notes** — Bioavailability, stability, formulation considerations
8. **Key gaps** — What the research doesn't answer

### Hypothesis Pages

Hypotheses are first-class pages representing testable claims about how supplements affect health outcomes through specific mechanisms. Each hypothesis connects supplements → pathways → outcomes with evidence and status.

A hypothesis should be created when:
- A claim spans multiple supplements (e.g., "Nrf2 activators provide cancer chemoprevention")
- A claim has meaningful tensions or contradictions worth tracking
- A claim is central to a stack decision and deserves its own scrutiny

Single-supplement claims can live in the supplement's evidence table. Promote them to hypothesis pages when they become important enough to track independently.

Each hypothesis page includes:
1. **Claim** — The testable hypothesis stated precisely
2. **Chain** — supplement(s) → pathway(s) → outcome(s) as wikilinks
3. **Supporting evidence** — Organized by evidence level
4. **Contradicting evidence** — What pushes against the hypothesis
5. **Tensions and nuances** — Boundary conditions, paradoxes, population-specific effects
6. **Status** — open, supported, contradicted, or nuanced
7. **What would confirm/refute** — What evidence would change the status
8. **Open questions** — `[!gap]` callouts for what's unknown

### Stack Pages

Stack pages represent combinations of supplements with a shared goal. Each stack page includes:

1. **Goal** — What the stack targets (e.g., "longevity baseline", "cognitive enhancement")
2. **Composition** — Supplements, doses, timing
3. **Rationale** — Why each supplement is included, how they complement each other
4. **Interaction check** — Known synergies or conflicts between stack components
5. **Evidence assessment** — Overall strength of evidence for the stack as a whole
6. **Open questions** — What needs more research

### Query

Answer questions using the wiki's accumulated knowledge. Read `purpose.md` for context. Search the index and wiki, read relevant pages, follow links. Cite specific pages. Distinguish sourced claims from inferences. If the answer is valuable — synthesizes multiple pages, resolves a recurring question, or would take significant reconstruction — file it as a new page in `wiki/queries/`.

### Lint

Health-check the wiki: orphans, dead ends, unresolved links, unverified claims, gaps. Validate frontmatter, index consistency, and cross-references. Check for supplement entity pages missing required sections. **Staleness check:** compare `raw_hash` values on source-summary pages against current files in `raw/` — flag any mismatches. Present findings by category; apply fixes only with human approval.

### Synthesis

`wiki/synthesis.md` is your evolving thesis on supplementation for longevity. Revise on every ingest. Keep under ~1,000 words. Reflect the full wiki, not just the latest source.

Prescribed sections:
1. **Strongest evidence** — Claims with level 3–4 evidence. What the wiki most confidently supports.
2. **Active debates** — Contested or nuanced claims. Link to [[Debates]] for detail.
3. **Best-guess stack** — Current best-supported combination with brief rationale. Evolves as evidence accumulates.
4. **Priority gaps** — Top 3–5 questions most worth researching next. Link to [[Research Backlog]].

Use `[!source]` only when referencing specific wiki pages directly. Use `[!analysis]` for cross-wiki synthesis.

### Debates

`wiki/debates.md` surfaces active disagreements: claims where sources contradict each other, or hypotheses with status `nuanced` or `contradicted`. It is DataView-driven for hypothesis-level debates, with a manual section for source-level disagreements that don't yet have a hypothesis page.

When ingesting a source that contradicts an existing claim, add a note to the manual section of `wiki/debates.md` linking both sources and the affected page. Promote to a hypothesis page if the tension is significant enough to track independently.

Use `obsidian append` to add to the manual section.

### Decisions Log

`wiki/decisions.md` is an append-only log of significant structural decisions: why a page was split, why a hypothesis was classified "nuanced" vs "supported", why a concept was scoped a certain way. Captures rationale that would otherwise be lost between sessions.

Append an entry when you make a non-obvious structural choice. Format:
`### [YYYY-MM-DD] decision | rationale`

Use `obsidian append` to add entries. Do not rewrite past entries.
